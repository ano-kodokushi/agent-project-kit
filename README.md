# agent-project-kit

让 AI 编码助手稳定干活的最小治理套件：四个文档 + 两个脚本，把"靠模型自觉"换成"靠机器执行"。

与具体产品无关。只要你的助手会读仓库根目录的 `AGENTS.md`，Claude Code、Codex、Cursor 或自建的 agent 都能用。

## 它解决的那个循环

AI 写代码时最常见的失败不是写错，而是这个循环：

```
① 它说"已完成"        →  ② 你没验就信了    →  ③ 三天后发现没做完
        ↑                                              │
        └──────── 重讲一遍需求、重踩一遍坑 ─────────────┘
```

每转一圈，付出的是返工加上重新交代上下文的成本。四份文档断掉②，两个脚本断掉①。

三种典型症状，中了才值得用：

| 症状 | 表现 | 对策 |
|---|---|---|
| 说完成其实没验 | "已实现并通过测试"，其实没跑 | `AGENTS.md` 要求写可复制的验收命令，任务卡必须带通过标准 |
| 换个会话就断片 | 上一轮的结论和踩过的坑全丢了 | `docs/BOARD.md` 作为唯一真相源，交接写在文件里而不是聊天里 |
| 跑偏没人拦 | 让它改 A，它顺手重构了 B 和 C | `push-task.mjs` 拒绝在 `main` 上直接提交，强制走任务分支 |

三条都没中，这套东西只会增加写文档的负担。

## 规矩由脚本执行，不由提示词执行

治理书里写"禁止直接向 main 提交"拦不住人，所以交给脚本：

```console
$ node push-task.mjs . -m "hotfix: 紧急修一下"
FAIL   当前在 main 上。治理书 §3 禁止直接向 main 提交。
       先开分支: git switch -c feat/T-xxx-描述
       （本脚本不会替你开分支——分支名是有意义的，得你或 Agent 起）
```

同一个脚本还会拒绝空提交、缺提交信息、没配远端，并在非快进合并时中止并切回原分支，不改写历史。

## 验证：七步闭环，每步断言

```bash
git clone https://github.com/ano-kodokushi/agent-project-kit
cd agent-project-kit
node examples/run-example.mjs
```

它会在系统临时目录里建一个真实项目，调用真实的 `bootstrap.mjs` 与 `push-task.mjs` 走完
「装机 → 开分支 → 干活 → 推分支 → 合并」整条闭环，任一步失败即非零退出。

远端用的是本地裸仓库，所以零凭据、离线可跑。这是本仓库的回归测试，不是演示数据。

期望结尾：

```
PASS  远端 main == 本地 main
PASS  远端有 2 个提交（初始 + T-101）
PASS  远端有 main 与任务分支
PASS  工作区干净

===== 示例闭环全部通过 =====
```

## 四份文档为什么非分开不可

四个坑，每个都对应一份文档：

| 坑 | 代价 |
|---|---|
| 跑偏没人知道 | 说"改 A"，它顺手重构了 B、C，review 成本翻倍 |
| 说完成其实没验 | 你替它跑验收；或者更糟，上线后才发现 |
| 换个会话就断片 | 重新交代上下文，等于把上一轮的钱再花一遍 |
| 越干越贵 | 每次开工都把全部历史读一遍 |

| 文件 | 作用 | 谁写 | 频率 |
|---|---|---|---|
| `AGENTS.md` | 怎么做事的规矩（红线、验收命令、目录约定） | 人，一次性 | 很少改 |
| `docs/TASK_BRIEF.md` | 做什么、做到什么算完 | 人，开工前 | 需求变更时 |
| `docs/PLAN.md` | 按什么顺序做（带可执行验收的任务卡） | 人与 Agent 共同 | 每个里程碑 |
| `docs/BOARD.md` | 做到哪了、卡在哪 | Agent 每次更新 | 每次任务 |

两个脚本把最容易违反的两条规矩变成机器约束：

| 脚本 | 干什么 |
|---|---|
| `bootstrap.mjs` | 一键装机：初始化 git → 配远端 → 复制四件套 → 首次提交 |
| `push-task.mjs` | 任务闭环：提交 → 推分支 → 合并 `main` → 推 `main` |

## 快速开始

需要 Node ≥ 18。git 在不在 `PATH` 里都行，脚本会自己找。

```bash
# 1) 装机（--dry-run 先看它要做什么，不写任何东西）
node bootstrap.mjs "/path/to/my-app" --remote "git@github.com:me/my-app.git" --dry-run
node bootstrap.mjs "/path/to/my-app" --remote "git@github.com:me/my-app.git"

# 2) 干活
cd /path/to/my-app
git switch -c feat/T-012-user-login
#   ...改代码、跑验收...
node /path/to/agent-project-kit/push-task.mjs "$PWD" -m "feat(T-012): 用户登录"
```

`bootstrap.mjs`：已存在的文件一律跳过、绝不覆盖（这四份文档是长期积累，覆盖等于清空）；
没给 `--remote` 时打印补配远端的两条命令；`--dry-run` 只打印计划。

`push-task.mjs` 的行为：

| 情况 | 行为 |
|---|---|
| 当前在 `main` 上 | 拒绝，并告诉你怎么开分支（不替你建，分支名承载任务语义） |
| 工作区无改动 | 拒绝产生空提交 |
| 缺 `-m` | 拒绝 |
| 没配 `origin` | 拒绝 |
| 非快进合并 | 中止合并、切回原分支，不改写任何历史 |
| `--no-merge` | 推分支就停，留给你建 PR |
| `--dry-run` | 只打印计划 |

## 指导思想

需要模型自觉遵守的，写进文档；需要机器强制执行的，写脚本、插件或 CI。

文档层的东西不适合做成插件：它们要进 git、能 diff、能评审、能被 review，绑进插件就失去版本管理。
但反复被漏做的环节（总忘记开分支、总忘记跑测试）值得写成强制脚本 —— `push-task.mjs` 就是这么来的：
治理书里写着"禁止直接向 main 提交"，而提示词拦不住人，于是让脚本直接拒绝。

判断标准：一条规矩已经写在文档里、却被违反了两次以上，就该把它变成脚本。

## 上手顺序

不要一次全填满。按下面的顺序加，每加一层跑一两天再看要不要继续：

1. 先上 git 与远端：用 `bootstrap.mjs`，或自己 `git init`
2. 写 `docs/TASK_BRIEF.md`：只填「背景与目标」「范围内 / 范围外」「验收标准」三节就能开工
3. 写 `AGENTS.md`：两节必须填实，它们是 Agent 的入口信息 ——
   §0 项目速览（项目名 / 一句话目标 / 技术栈 / 当前阶段）与 §6 验收命令（可直接复制的命令）；
   §7「绝对禁止」照抄即可，性价比最高
4. 项目超过 10 个任务后，再补 `docs/PLAN.md` 与 `docs/BOARD.md`

## 脚本里那些"多余"的防御

读代码时如果觉得有些地方过度小心，那是因为它们踩过：

| 代码里的做法 | 为什么 |
|---|---|
| 找 git 时先试绝对路径、再扫 `PATH` | 某些托管或沙箱环境里 `PATH` 是空字符串，裸调 `git` 直接失败 |
| 拒绝在 `main` 上提交 | 文档里写"禁止直接提交 main"被违反过；提示词拦不住，脚本能 |
| 非快进时中止并切回，不自动 rebase | 改写历史是危险操作，该由人决定，不该由脚本代劳 |
| 绝不覆盖已有文件 | 覆盖一次，前面几个月积累的 `BOARD` 历史就没了 |

需要覆盖 git 路径时设环境变量：

```bash
DSH_GIT=/usr/bin/git node push-task.mjs "$PWD" -m "chore: x"
```

## 目录结构

```
agent-project-kit/
├── LICENSE
├── README.md
├── bootstrap.mjs              # 一键装机
├── push-task.mjs              # 任务闭环推送
├── AGENTS.md                  # 模板：仓库治理书
├── examples/                  # 可跑的回归测试（见下）
└── docs/
    ├── TASK_BRIEF.md          # 模板：项目任务书
    ├── PLAN.md                # 模板：执行计划书
    └── BOARD.md               # 模板：协调板
```

模板约定：`<!-- 填写 -->` 是待替换的占位内容；`### T-XXX` 是示例任务，可直接删掉替换；
方括号 `[ ]` 是勾选框，完成后改成 `[x]`。

## 可跑示例：七步闭环

`examples/` 里的最小示例是本仓库的回归测试 —— 改了脚本之后跑一遍就知道有没有弄坏。

| 步 | 做什么 |
|---|---|
| ① | 把 `examples/todo-cli` 复制到系统临时目录 |
| ② | 建一个本地裸仓库当远端 |
| ③ | 调真实 `bootstrap.mjs` 装配（含配远端、首次提交） |
| ④ | 开任务分支 `feat/T-101-…` |
| ⑤ | 实现 `docs/TASK-T101.md` 那张卡 |
| ⑥ | 跑该卡的验收命令（`node test/run.js`，期望 PASS 7/7） |
| ⑦ | 调真实 `push-task.mjs` 收口：提交 → 推分支 → 合并 `main` → 推 `main` |

远端用本地裸仓库，是为了让示例离线可跑、零凭据；否则别人 clone 下来第一步就卡在配 SSH key 上。

示例里的 `T-101` 不是"加个函数"那么简单：加输出前缀会破坏一条把旧输出写死在多行字符串里的既有断言。
它顺带演示了真实工作里最常见的坑 —— 改行为时要搜全所有断言，别只改第一眼看到的那条。
