# agent-project-kit

**让你的 AI 编码助手稳定干活的最小治理套件。**
四个文档 + 两个脚本，把「靠模型自觉」变成「靠机器执行」。

> 与具体产品无关：不管你用 Claude Code、Codex、Cursor 还是自己搭的 agent，
> 只要它**会读仓库根目录的 `AGENTS.md`**，这套东西就能用。

---

## 它解决什么问题

让 AI 写代码，反复踩这几个坑：

| 坑 | 表现 |
|---|---|
| **跑偏没人知道** | 你说"改 A"，它顺手重构了 B、C |
| **说完成其实没验** | "已实现并通过测试"——其实没跑 |
| **换个会话就断片** | 上一轮的结论、踩过的坑全丢了 |
| **越干越贵** | 每次开工都把全部历史读一遍 |

这套东西对应四份文档，**各管一件事，互不重叠**：

| 文件 | 作用 | 谁写 | 频率 |
|---|---|---|---|
| `AGENTS.md` | **怎么做事的规矩**（红线、验收命令、目录约定） | 人，一次性 | 很少改 |
| `docs/TASK_BRIEF.md` | **做什么、做到什么算完** | 人，开工前 | 需求变更时 |
| `docs/PLAN.md` | **按什么顺序做**（带可执行验收的任务卡） | 人与 Agent 共同 | 每个里程碑 |
| `docs/BOARD.md` | **做到哪了、卡在哪** | Agent 每次更新 | 每次任务 |

加两个脚本，把两条最容易违反的规矩变成**机器约束**：

| 脚本 | 干什么 |
|---|---|
| `bootstrap.mjs` | 一键装机：初始化 git → 配远端 → 复制四件套 → 首次提交 |
| `push-task.mjs` | 任务闭环：提交 → 推分支 → 合并 `main` → 推 `main` |

## 快速开始

需要 Node ≥ 18。git 有没有在 PATH 里都行（脚本会自己找）。

```bash
# 1) 装机（--dry-run 先看它要做什么，不写任何东西）
node bootstrap.mjs "/path/to/my-app" --remote "git@github.com:me/my-app.git" --dry-run
node bootstrap.mjs "/path/to/my-app" --remote "git@github.com:me/my-app.git"

# 2) 干活
cd /path/to/my-app
git switch -c feat/T-012-user-login
#   ...改代码、跑验收...
node /path/to/agent-project-kit/push-task.mjs "$PWD" -m "feat(T-012): 用户登录"
```

`bootstrap.mjs` 的几条保证：

- **已存在的文件一律跳过，绝不覆盖** —— 这四份文档是长期积累，覆盖等于清空
- 没给 `--remote` 时，会打印补配远端的两条命令
- `--dry-run` 只打印计划，不写任何文件

`push-task.mjs` 的几条硬规矩：

| 情况 | 行为 |
|---|---|
| 当前在 `main` 上 | **拒绝**，并告诉你怎么开分支（不替你建——分支名承载任务语义） |
| 工作区无改动 | **拒绝**产生空提交 |
| 缺 `-m` | **拒绝** |
| 没配 `origin` | **拒绝** |
| 非快进合并 | **中止合并、切回原分支**，不改写任何历史 |
| `--no-merge` | 推分支就停，留给你建 PR |
| `--dry-run` | 只打印计划 |

## 使用心法（这是全套东西的指导思想）

> **需要模型「自觉遵守」的 → 写进文档**
> **需要机器「强制执行」的 → 写脚本 / 插件 / CI**

文档层的东西**别**做成插件：它们要进 git、能 diff、能评审、能被 review。
绑进插件就失去了版本管理。

但**反复发现 Agent 漏做的环节**（总忘记开分支、总忘记跑测试），
那就值得写成强制脚本——`push-task.mjs` 就是这么来的：
治理书里写着"禁止直接向 main 提交"，但**提示词拦不住人**，所以让脚本直接拒绝。

**判断标准**：一个规矩你已经写在文档里、但被违反了两次以上 → 把它变成脚本。

## 上手顺序

不要一次全填满。按下面的顺序加，每加一层跑一两天再看要不要继续：

1. **先上 git + 远端** —— 用 `bootstrap.mjs`，或自己 `git init`
2. **写 `TASK_BRIEF.md`** —— 只填「背景与目标」「范围内 / 范围外」「验收标准」三节就能开工
3. **写 `AGENTS.md`** —— 有两节**必须填实**，它们是 Agent 的入口信息：
   - **§0 项目速览**（项目名 / 一句话目标 / 技术栈 / 当前阶段）
   - **§6 验收命令**（改完代码怎么验证，写可直接复制的命令）
   第 §7「绝对禁止」照抄即可，最高性价比
4. **项目超过 10 个任务后**，再补 `PLAN.md` 和 `BOARD.md`

## 为什么脚本里有些"多余"的防御

如果你读代码觉得有些地方过度小心，那是因为它们**真的踩过**：

| 代码里的做法 | 为什么 |
|---|---|
| 找 git 时先试绝对路径、再扫 `PATH` | 某些托管/沙箱环境里 **`PATH` 是空字符串**，裸调 `git` 直接失败。这不是臆想 |
| `push-task.mjs` 拒绝在 `main` 上提交 | 文档里写"禁止直接提交 main"**被违反过**——提示词拦不住，脚本能 |
| 非快进合并时**中止并切回**，不自动 rebase | 改写历史是危险操作，应该由人决定，不该由脚本"帮忙" |
| `bootstrap.mjs` 绝不覆盖已有文件 | 覆盖一次，前面几个月积累的 `BOARD` 历史就没了 |

需要覆盖 git 路径时设环境变量：

```bash
DSH_GIT=/usr/bin/git node push-task.mjs "$PWD" -m "chore: x"
```

## 目录结构

```
agent-project-kit/
├── LICENSE
├── README.md
├── bootstrap.mjs              # 一键装机
├── push-task.mjs              # 任务闭环推送
├── AGENTS.md                  # 模板：仓库治理书
└── docs/
    ├── TASK_BRIEF.md          # 模板：项目任务书
    ├── PLAN.md                # 模板：执行计划书
    └── BOARD.md               # 模板：协调板
```

## 模板约定

- `<!-- 填写 -->` 是需要你替换的占位内容
- `### T-XXX` 这类是示例任务，可直接删掉替换
- 方括号 `[ ]` 是勾选框，完成后改成 `[x]`
